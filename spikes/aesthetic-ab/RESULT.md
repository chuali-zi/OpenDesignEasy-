# 审美对比实验：破解「AI 味」的三条路线

> ⚠️ **本文档的两条结论已被第二轮实验推翻，读之前先看 [`RESULT2.md`](RESULT2.md)：**
> - **§4.2「Tailwind 必须走 CDN，C 组要付架构上最大的代价」——错。** 离线 vendor 包后
>   6/6 产物在零网络下渲染，指标与联网版逐项一致。而且本轮漏掉了 A2/B1/B2 同样在拉
>   Google Fonts：离线资产供给是所有路线的共同前提，不是框架路线的专属代价。
> - **§3.1/§4.1「B 组 token 纪律差 4-6 倍」——量错了层。** 整页口径把工作台外壳和预览区里的
>   产物算成了一层。分层重测后 B2 的内层产物只有 4 色、比外壳还少、整页数等于外壳数——
>   它根本没做出独立的产物。整页数低是**两层未隔离**的结果，被读成了纪律好。
>
> §3.2（反常动作确实落地）、§3.4（必须走流式）、§4.3（B 组内容更弱、手法收敛）仍然成立；
> 其中 §4.3 的第二条在第二轮以 n=5 被坐实。

> 状态：**6/6 生成 + 渲染完成。审美结论待人工审核**（`report.html`）。
> 日期：2026-07-29。模型：Kimi `k3`，流式，`max_tokens=40000`。
> 报告页：[`report.html`](report.html)。原始数据：`runs/`、`shots/`、`shots_summary.json`。

## 1. 要检验的问题

用户反馈：agent 产出的前端**过程令人满意、成品「AI 味」太重、难看**。

我的诊断：**问题不是布局，是「没有观点」。** E4 那批产物的布局其实没问题（Q1 在干净页上
0 违规、无溢出、无对比度问题）。丑在深蓝灰底 + 青紫点缀 + 系统字体栈 + 均匀节奏 —— 这是训练分布的
**众数**。模型在做求平均，而设计的本质是有一个明确观点。

用户倾向「搬前端设计框架/模板过来」。我提出反对意见（换成 framework 味、与无网络沙箱冲突、
修的是本来没坏的布局），并反提议「处方性艺术方向」。**双方都不确定，所以做实验。**

## 2. 实验设计

三组，同一份 brief（两栏：左窄聊天 / 右大预览，类 Claude artifact 心智模型），每组 2 次：

| 组 | 做法 |
|---|---|
| **A** baseline | 把 brief 直接交给 agent，不加审美约束。对照组。 |
| **B** 处方性艺术方向 | 两阶段。先让 agent 以「艺术指导」身份输出确切色值/字体配对/字号阶/间距阶/版式原型/**一处刻意的反常动作** + 理由，再以「工程师」身份严格按它实现，禁止引入方向外的新值。 |
| **C** 组件框架 | 引入 Tailwind CDN，按成熟组件模式（shadcn/Tailwind UI 风格）实现。 |

**反均值化装置是「强制显式承诺 + 必须越界一次」，不是策展库的大小。** B 组没有用任何外部
配色库——方向由 agent 自己定，只是被强制先说出来、且必须包含一处别人不会那么干的决定。

## 3. 客观结果

### 3.1 设计 token 纪律性（本实验最硬的发现）

用 D3 的计算样式抽取器（`spikes/q1-checks/lib/extract_computed.py`）测产物**实际渲染后**用了多少 token：

| 产物 | 实际颜色数 | 字号阶数 | 首选字体 | 总 token | 耗时 |
|---|---:|---:|---|---:|---:|
| A1 baseline | **31** | **21** | `-apple-system` | 21,944 | 568s |
| A2 baseline | **23** | **27** | `JetBrains Mono` | 11,387 | 274s |
| **B1 艺术方向** | **7** | **6** | `IBM Plex Mono` | 13,864 | 338s |
| **B2 艺术方向** | **5** | **7** | `IBM Plex Mono` | 13,319 | 390s |
| C1 Tailwind | 17 | 9 | `JetBrains Mono` | 21,058 | 582s |
| C2 Tailwind | 30 | 12 | `-apple-system` | 27,906 | 765s |

**A 组用了 23–31 个颜色、21–27 个字号阶。** 这不是设计，是堆砌——一个页面用 27 个不同字号，
说明字号是逐处拍的，不存在阶梯。

**B 组 5–7 个颜色、6–7 个字号阶**，因为艺术方向规定了确切阶梯且禁止引入新值，而 stage 2 的
系统提示把它作为铁律。**这是数量级差异，不是主观判断。**

C 组介于中间：Tailwind 的字号阶帮它把字号收到 9–12（比 A 组好），但**颜色仍然发散到 17–30**
——Tailwind 的调色板太大，不构成约束。

### 3.2 「刻意的反常动作」是否真的落地

两次都落地了，且两次都独立收敛到同一类手法（超大版本号），这本身值得注意：

| 组 | 方向名 | 强调色 | 反常动作 | 截图验证 |
|---|---|---|---|---|
| B1 | 打样房 Proof Room | `#E8490F` | 版本号 `v3` 以 96px 衬线字作「批次章」压在预览区右上角 | ✅ 已落地，红色 v3 明显可见 |
| B2 | 校对样张 Proof Sheet | `#D64B1E` | 版本号用 Fraunces 96px，比页面任何标题大 4 倍，且只有它用朱橙色；对话栏反而压到 13px | ✅ 见 report.html |

### 3.3 渲染健康

6/6 全部 0 console error、0 失败请求、锚点完整（section 6–12 / object 6–17）。
**C 组的外链放行数为 0** 是因为我在渲染器里显式放行了 Tailwind CDN —— 这不是「C 组不需要网络」，
恰恰相反，见 §4.2。

### 3.4 一个基础设施发现

`max_tokens=40000` 非流式请求**被 endpoint 的 nginx 打 504** —— 生成期间不发任何字节，网关判超时。
必须走流式（`stream=True` + `stream_options.include_usage`）。这不是预算选择问题，是基础设施约束，
已写入 `spikes/_lib/kimi.py` 的 `chat_stream()`。

E4 当初 16000 撞顶截断的问题，在流式 + 40000 下**6/6 全部 `finish_reason=stop`，无一截断**。

## 4. 结论

### 4.1 B 组在客观指标上明确胜出

token 纪律性差 4–6 倍，成本还更低（13k vs A 的 11–22k、C 的 21–28k）——因为它不乱试。

**但「好看」是主观的，这份报告不下这个结论。** 需要用户看 `report.html` 判断。

我能负责地说的是：**A 组那种 31 色 / 27 字号阶的产物，在任何设计标准下都属于没有设计。**
B 组至少是「有一个可辩护的观点并被贯彻」。这两者的差距是可测的。

### 4.2 C 组的代价被实验坐实了

Tailwind 必须走 CDN，意味着**渲染沙箱必须放行网络**——而我们刚用 AppContainer 把网络彻底关掉
（spike E1，零 capability 连裸 IP 都拒）。为 C 组开这个口子，等于放弃刚证明的隔离，
或者要额外做「只放行特定域名」的白名单机制（AppContainer 的 capability 模型不支持按域名放行，
只能全开或全关——所以实际上要退回到代理/防火墙方案，而 E1 已经证明那些挡不住 raw socket）。

**C 组在客观指标上并没有压倒性优势**（颜色仍发散到 17–30，成本最高、最慢），
却要付出架构上最大的代价。这条不划算。

### 4.3 观察到的取舍（需要用户判断）

- **B 组视觉识别度强，但内容执行更弱**：B1 的左侧对话栏基本空着，而 brief 明确要求真实多轮对话。
  A/C 组的对话内容都做得更饱满。**可能原因**：stage 2 的注意力被「严守方向」占用。
  这是一个真实的取舍信号，不是我的推测——截图可验证。
- **B 组两次独立生成都收敛到「超大版本号」这一个手法**。样本只有 2，不能断言，
  但如果这是系统性的，说明「必须有一处反常」这个指令本身也会产生新的众数——
  **反均值化装置自己可能被均值化**。这需要更大样本验证。

## 5. 对 spec 的建议（待用户确认审美结论后再落）

1. **`design-intelligence-spec.md` §3 的 design contract 需要双向化。**
   现在它只是**描述性**的（生成后机械抽取，用于查漂移）。实验表明它还需要一个**处方性**形态：
   生成**前**给出的艺术方向。同一数据形状，两个方向：

   | 方向 | 时机 | 作用 |
   |---|---|---|
   | 处方（新增） | 生成前 | 约束创作，禁止求平均 |
   | 描述（现有） | 生成后 | 检测漂移 |

   **这个重构不破坏已冻结的 `quality-governance-spec.md` 与待冻的 `artifact-production-spec.md`**
   ——它们消费 contract 的方式完全不变。

2. **新增 §4.2.1 艺术方向阶段**，产出物是可独立审核的 artifact：用户可在写代码前否掉方向。
   这正面解决用户提出的「质量管理管理不了最开始的失败」——审美失败被拦在最便宜的位置。

3. **`agent-engine-spec.md` 不需要新增「套框架」类工具。** 实验不支持框架路线，
   因此不必为它引入 npm/build/CDN 相关工具，也不必动 §8 的无网络默认。

4. **如果用户仍想要框架路线**，那 `artifact-production-spec.md` §3/§6 必须修订以容纳构建步骤，
   且 ADR-0004 的沙箱方案要重新评估「按域名放行」的可行性（当前 AppContainer 模型做不到）。

## 6. 诚实说明

- **每组只有 2 个样本。** 用户指定「跑俩得了」。token 纪律性的差异极大（5 vs 31）所以结论稳；
  但「B 组内容执行更弱」「B 组收敛到同一手法」这两条观察 n=2，**不足以定论**。
- **我没有做审美判断**，§4.1 只声称「A 组在客观指标上属于没有设计」，这是 token 计数支撑的，
  不是好看与否的判断。
- B 组的两个艺术方向由 **agent 自己定**，没有使用任何外部策展库（如环境里可用的
  `ui-ux-pro-max` 提供 161 组配色 / 57 组字体配对）。**接入策展库是否会进一步提升，未测。**
- C 组只测了 Tailwind CDN，没测「真正搬一套完整模板/设计系统进来」（那需要 build 工具链，
  与当前无网络沙箱冲突，成本远超本实验范围）。因此**不能说「所有框架/模板路线都不行」**，
  只能说 Tailwind CDN 这条最轻量的框架路线没有体现出压倒性优势。
- 未真实执行任何模型产生的 shell 命令；产物均为静态文件 + 浏览器内 JS。
