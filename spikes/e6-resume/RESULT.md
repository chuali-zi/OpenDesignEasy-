# E6 Spike 结果：工作区 + turn history 续跑

> 状态：**已完成**，9/9 组对比数据齐备。
> 对应假设：`docs/spec/agent-engine-spec.md` §15 E6。
> 原始数据：`results/raw/*.json`（9 组）、`results/calibration_summary.json`。
> 报告由主 agent 从子 agent 留下的完整原始数据整理（子 agent 在写报告前被会话额度中断）。

## 1. 假设原文

> **E6**：工作区 + turn history 续跑能真正省掉重复工作。
> 判定标准：模拟进程重启，比较**续跑**与**从零重跑**的预算消耗。

## 2. 为什么这个 spike 重要

`agent-engine-spec.md` §7 做了一个关键设计决定：**不改 Phase 2 的 stage checkpoint 契约**。
理由是 agent 循环是 stage 内部过程，把每轮工具调用做成 sub-checkpoint 会污染 workflow 契约。
替代方案是「工作区持久 + turn history 持久 + stage 重入时从现状续跑」。

这个 spike 要验证该替代方案真的省事，而不是纸上谈兵。**如果续跑省不了多少，spec §7 的设计就
没有价值，应该重新考虑是否真要改 Phase 2 契约做细粒度 checkpoint。**

## 3. 方法

- 任务：让 k3 建一个 3 文件小站点（`index.html` + `styles.css` + `script.js`），每建完一个
  用 `read_file` 读回自查。校准运行（`calibration_summary.json`）确认无中断时需 **8 步**、
  16,098 token、53.3 s。
- 工具集限定为工作区内的 `read_file` / `write_file` / `list_files`，路径经
  `os.path.realpath` 校验后必须仍在工作区内。**不真实执行任何模型产生的命令**
  （沙箱 spike E1 结论未出时的安全约束）。
- 持久化：工作区 = 磁盘目录；turn history = `.agent/turns.json`；预算账本 = `.agent/budget.json`；
  工具日志 = `.agent/tool_log.json`。
- **中断点**：第 2、4、6 步（约对应校准 8 步的 25% / 50% / 75%），每个点重复 3 次，共 9 组。
- 每组跑两条路径：
  - **路径 A（续跑）**：从持久化的工作区现状 + turn history 恢复，继续跑到完成。
    计费**包含**崩溃前已消耗的预算——这是「这次事故总共花了多少」的公平口径。
  - **路径 B（重跑）**：清空工作区，从零开始跑到完成。
- 重复劳动判定：`duplicate_writes` = 续跑后又写了一遍崩溃前已写成功的同一路径；
  `duplicate_reads` 同理。

## 6. 结论：E6 **通过**，但收益低于直觉且不均匀

### 6.1 省，但只省三分之一左右

续跑相比从零重跑，**步数省 34%、时长省 34%、token 省 26%**（均值）。这是真实收益，
但**不是**「省掉崩溃前那部分工作」那么多——直觉上在第 6 步（75%）中断，续跑应该只需再花 25%，
实测却仍要花掉重跑的 64%。

原因在数据里很清楚：**prompt token 随历史累积**。续跑要把崩溃前的完整 turn history 重新发给模型，
所以「已完成的工作」虽然不用重做，但它的**上下文成本每一轮都要重付**。这与 D1 spike 的发现一致
（prompt : completion ≈ 6.7 : 1，见 `spikes/d1-agent-loop/RESULT.md` §6.3）。

### 6.2 一组出现负收益，必须如实记录

`ip4_r1` 的 token 节省是 **−13.6%**：续跑（19,964）比重跑（17,568）**更贵**。

原因：续跑那次模型多花了 1 步（9 步 vs 校准的 8 步），而重跑那次恰好走了较短路径（11 步但
每步上下文更短）。由于 k3 `temperature=1` 不可调（endpoint 硬性限制），单次运行方差较大，
9 组样本不足以完全消除。

**这意味着 spec 不能承诺「续跑一定更省」**，只能承诺「统计上更省，且不会重复劳动」。

### 6.3 最强的一条结论：零重复劳动

9 组、18 条路径、全部 0 次重复写、0 次重复读。模型在恢复后**正确识别了工作区已有内容**，
直接继续未完成的部分，没有出现「又建一遍已经存在的文件」。

这条比 token 节省更重要：它说明 `agent-engine-spec.md` §7 的「从工作区现状 + turn history
续跑」在**正确性**上成立，不只是省钱问题。如果模型会重复劳动，续跑就可能产生冲突写入或
覆盖已完成成果，那才是真正的设计缺陷。

### 6.4 回答派发时提的两个问题

**Q：续跑到底省多少？如果省得不明显，是否该改 Phase 2 契约做细粒度 checkpoint？**

省 26–34%，且零重复劳动、零正确性问题。**不建议改 Phase 2 契约。** 理由：
细粒度 sub-checkpoint 能进一步省下的主要是「重发历史」的 prompt 成本，而那部分更应该靠
**prompt caching**（endpoint 已支持，见 D1 §6.3）解决，而不是靠污染 workflow 契约。
`agent-engine-spec.md` §7「不改 Phase 2 契约」的决定**成立**。

**Q：续跑时模型重复劳动的问题严重吗？**

不严重——实测为零。因此 spec §7 **不需要**额外加「恢复时注入工作区摘要」的机制。
但建议保留这条作为**降级手段**写进 spec 备注：若换模型后出现重复劳动，注入摘要是已知解法。

## 7. 对 `agent-engine-spec.md` §7 的修订建议

1. **§7 的设计决定标记为已验证**，并引用本 spike 数据（26–34% 节省、零重复劳动）。

2. **措辞收紧**：把「续跑而非从零重跑」的收益表述为「**统计上**显著降低步数、时长与 token，
   且不产生重复劳动」，**不要**写成「一定更省」——实测 9 组里有 1 组 token 为负。

3. **补一条关于成本结构的说明**：续跑省下的是**执行**，不是**上下文**。历史仍需每轮重发，
   因此续跑收益上限受 prompt 累积约束。建议与 D1 §6.3 一起指向同一条结论：
   **agent 循环的主成本是 prompt 累积，压成本的主要手段是 prompt caching 而非细粒度 checkpoint。**

4. **新增降级备注**：若未来某个能力实例在续跑后出现重复劳动，可在恢复时额外注入一段
   「当前工作区已有什么」的确定性摘要。本次实测 k3 不需要该机制。

5. **§9 预算**：明确续跑时预算账本**不重置**——本 spike 已按此口径实现并验证（崩溃前消耗
   计入续跑总账），spec 该措辞成立，建议标注已验证。

## 8. 诚实说明

- 样本量 9 组，`temperature=1` 不可调导致单次方差较大；token 节省的置信区间较宽，
  报告中给的是 min/中位/max/均值全量而非单一数字。
- 任务是 3 文件静态站点，**不含渲染自验证**。真实候选创作的续跑收益可能不同——
  截图回传会进一步抬高 prompt 累积，理论上会**降低**续跑的相对收益百分比。未外推。
- 「模拟崩溃」是在第 N 步主动停止循环，不是真实进程被杀。真实场景下可能出现
  工具调用执行到一半的部分写入（写文件中途断电），本 spike **未覆盖**该情形。
  建议后续补一个「部分写入」的恢复测试。
- 未真实执行任何模型产生的命令。
