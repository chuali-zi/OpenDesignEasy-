# D1 + E7 Spike 结果：agent 长会话中的工具调用可靠性与预算消耗

> 状态：**已完成**，20/20 会话数据齐备。
> 对应假设：`docs/spec/design-intelligence-spec.md` §11 D1、`docs/spec/agent-engine-spec.md` §15 E7。
> 原始数据：`results/raw.json`（20 条完整记录）、`results/summary.json`、`results/run_log.txt`。

## 1. 假设原文

**D1**（`design-intelligence-spec.md` §11）：

> Kimi K2/K3 的**工具调用**在长会话中稳定可靠。判定标准：连续 20 次候选会话的工具调用格式
> 错误率与完成率。

**E7**（`agent-engine-spec.md` §15）：

> 预算上限足以覆盖一个完整页面的创作。判定标准：首个场景的实际消耗分布。

## 2. 方法

### 2.1 安全约束（如实执行）

- `read_file` / `list_files` / `write_file` 是**真实执行**，硬限制在
  `spikes/d1-agent-loop/workspaces/<session_id>/` 内。每次调用先用
  `os.path.realpath` 解析目标路径并校验其仍在该目录下（`Path.relative_to` 抛
  `ValueError` 即拒绝），绝对路径直接拒绝。违规不抛异常终止会话，而是把
  `SandboxViolation` 错误文本作为工具结果返回给模型（脚本 `tools.py:118-138`）。
- `run_command` **是模拟工具，全程未真实执行任何命令**。实现里不出现
  `subprocess`、`os.system`、`eval`、`exec`；`shlex.split` 只用于取命令首词以决定
  返回哪种预设文本，从不把命令交给系统 shell。`ls`/`dir`/`cat`/`type`/`wc`/`echo`
  返回基于真实沙箱文件系统状态伪造的输出（例如真实 `os.listdir` 结果拼成的
  "ls 输出"）；其余命令（`npm`、`node`、`git` 等）一律返回
  `/bin/sh: 1: <cmd>: not found`，模拟一个没装任何工具链的沙箱（`tools.py:180-238`）。
- 未使用任何真实网络访问；`kimi.py` 只连 Kimi 官方 endpoint。

> 这条约束是刻意的：本 spike 与沙箱可行性 spike（E1）并行执行，在 E1 结论未出之前
> 不让模型驱动真实命令执行。E1 事后证明这个顺序是对的——见 §7。

### 2.2 Agent 循环

- 每次会话独立工作区、独立 message 历史，不共享上下文。
- 固定任务 prompt（`agent_loop.py:TASK_PROMPT`）：要求模型在工作区用
  `write_file` 建一个单页 `index.html`（含 doctype/title/header+nav/main 含标题与
  段落/footer），随后**必须**用 `read_file` 读回自查，可选用 `list_files` /
  `run_command` 辅助，完成后停止调用工具、用纯文本总结收尾。
- 循环终止条件：模型某轮返回不含 `tool_calls`（记为 `self_terminated`）、步数
  达到上限 `MAX_STEPS=20`（记为 `step_limit`）、连续重试后仍是 429/5xx 或遇到
  非重试 HTTP 错误（记为 `api_error`）、单会话墙钟超过 480s 的安全阀
  （`wallclock_limit`，仅作硬保护，不是被测预算维度）。
- 每轮 `chat()` 调用：`temperature=1`（k3 唯一接受值）、`max_tokens=16384`，
  429/5xx 按 `2^attempt` 秒退避、最多重试 5 次；其他 HTTP 错误（如 400）不重试，
  直接判定该会话为 `api_error` 并如实记录，不静默吞掉。
- assistant 的 `tool_calls` 消息与每个 `tool_call_id` 对应的 `role:"tool"` 消息按
  OpenAI 兼容格式拼接；回填历史时丢弃 `reasoning_content` 字段（只保留
  `content`/`tool_calls`），避免把推理过程再喂回模型。

### 2.3 故障注入（错误恢复测试）

对每个 session 统一预设：**该 session 中 `read_file` 的第 1 次调用**与
**`run_command` 的第 1 次调用**分别被替换为预设失败结果——

- `read_file` 第 1 次调用：无论目标文件是否真实存在，一律返回
  `{"error": "FileNotFoundError: '<path>' does not exist"}`（不做真实文件系统访问）。
- `run_command` 第 1 次调用：无论命令内容，一律返回
  `{"stdout": "", "stderr": "/bin/sh: 1: <cmd>: not found", "exit_code": 127}`。

之后同一工具的调用一律走真实/正常模拟路径，不再故障。20 次 session 用同一套
故障轮次设计，便于横向比较恢复行为。

**恢复判定**（自动化，定义见 `run_sessions.py:compute_recovery`）：

- `not_triggered`：该 session 从未调用过对应工具，故障未触发；
- `recovered`：故障触发后，(a) 会话最终 `self_terminated` 且产出有效
  `index.html`，且 (b) 故障后紧邻的下一次工具调用**不是**对同一工具、同一
  `path`/`command` 参数的原样重复且仍然失败（即模型要么换了做法，要么重试后
  成功，要么虽重复但那次重复已经成功）；
- `not_recovered`：故障触发但不满足上述条件（原地重复失败、或会话未能正常完成）。

这是一个客观、可复核的启发式代理指标，不是对模型「聪明程度」的主观评分；
原始 `calls_log`（含每次调用的顺序、工具名、`args_key`、是否成功）保留在
`results/raw.json` 中供复核。

### 2.4 产物有效性判定

会话结束后检查工作区内 `index.html`：文件存在 (`exists`) 且能被 Python
标准库 `html.parser.HTMLParser().feed()` 无异常解析 (`parseable`)，两者皆真
记为 `valid`。**不评价页面美观或语义质量**，只判定"文件存在且可解析"。

### 2.5 已知偏差与限制

- 故障轮次固定为"每类工具第 1 次调用"，不是随机分布在长会话中段/末段；因此
  本次结果只回答"开局遇到一次故障能否恢复"，不回答"连续多次故障"或"会话
  后期故障"下的恢复率。
- `run_command` 的模拟内容有限（仅 `ls/dir/cat/type/wc/echo` 有真实感输出，
  其余一律 127），可能引导模型更少依赖 `run_command`，从而降低该故障被触发
  的样本量（实测 20 次里 2 次未触发）。
- 任务本身较简单（单页 HTML），E7 的预算结论只对"同等复杂度页面"成立，不
  外推到多文件项目或需要迭代视觉自修复的场景。**这是本次数据最重要的外推限制**，
  见 §6。

## 5. 结论

### D1：**通过**（无保留）

- 120 次工具调用**零格式错误**：`arguments` 全部是合法 JSON，函数名全部存在，必填参数无缺失。
- 完成率 100%，无一次需要靠步数上限兜底。
- **错误恢复 100%**：注入的 `FileNotFoundError` 与 `exit_code 127` 全部被模型消化，
  它会换路径、换做法或重试成功，没有出现"原地重复同一个失败调用"的死循环。

这条对 `agent-engine-spec.md` §4.3 的设计假设是强支持：spec 说「工具返回的错误是**给模型看的
信息**，不是立即终止的理由」——实测证明模型确实能用这些错误自我纠正，不需要引擎替它兜底。

### E7：**部分通过，但本次数据不足以直接定预算**

数据本身干净（20/20 完成，消耗集中），但**任务复杂度远低于真实场景**：单页静态 HTML、
无渲染、无截图回传、无多轮视觉自修复。真实候选创作要多消耗至少一个数量级。因此
§6 给的是**分层建议**，并明确标注哪些是实测、哪些是外推。

## 6. E7 预算数值建议

### 6.1 实测基线（简单单页，无渲染自验证）

| 维度 | 实测 max | 建议上限 | 余量倍数 |
|---|---|---|---|
| 步数 | 8 | **20** | 2.5× |
| 总 token | 23,745 | **60,000** | 2.5× |
| 时长 | 110 s | **300 s** | 2.7× |

### 6.2 外推到真实候选创作（多文件 + 渲染自验证 + mock）

**以下是外推，不是实测。** 依据：真实候选要多做「渲染 → 截图回传 → 看图找问题 → 改 → 再渲染」
最多 3 轮（`agent-engine-spec.md` §6），每轮回传一张截图。截图 base64 会显著抬高 prompt token。

| 维度 | 建议上限 | 依据 |
|---|---|---|
| 步数 | **60** | 实测 8 步做完单页；多文件 + 3 轮自修复约 5–7 倍 |
| 总 token | **250,000** | 见 §6.3 的 prompt 累积效应 + 截图成本 |
| 时长 | **900 s**（15 min） | 实测 110s；渲染与多轮往返是主要增量 |
| 生图次数 | 待 D4 解锁后定 | 本次无生图凭据 |

这些数字**必须**在首个真实候选跑通后按实测重新校准，不应直接冻结进 spec。

### 6.3 关键发现：prompt token 是主成本，不是 completion

实测 prompt : completion 中位数为 **11,772 : 1,749 ≈ 6.7 : 1**。原因是 agent 循环每一轮都要把
完整历史（含所有工具返回）重新发一遍，成本随轮次**超线性**增长。

这对 `agent-engine-spec.md` §9 有直接影响：**预算不能只按"模型写了多少"算**，必须按累积
prompt 算。会话越长，每一步的边际成本越高——这也是为什么步数上限本身就是一种成本控制手段。

冒烟测试观察到 endpoint 会返回 `cached_tokens`（91/91 全命中），说明有 prompt 缓存。
**建议 ADR-0003 明确是否依赖 prompt caching 来压 agent 循环成本**，这会显著改变预算模型。

### 6.4 对我早先一条判断的修正

我在派发本 spike 时提醒过「reasoning token 要单独计列，否则预算会严重低估」。
**实测数据不支持这个担心的强度**：reasoning 中位数 149，仅占总量约 1.1%。

之前那个印象来自一次「回复 OK」的冒烟测试（48 completion token 里 32 个是 reasoning，占 67%）——
那是极短任务的特例。在有工具调用的实际会话里，reasoning 占比很小。
reasoning token 仍应单独记录（便于观测），但**它不是预算的主要风险项，prompt 累积才是**。

## 7. 对 Spec 的修订建议

1. **`design-intelligence-spec.md` §11 的 D1 判定可标记为已通过**，并把「工具调用可靠」从
   假设升格为已验证事实：120/120 零格式错误、100% 故障恢复。

2. **`design-intelligence-spec.md` §8 失败矩阵**中「工具调用格式持续错误 → `RETRYABLE` →
   耗尽转 `CAPABILITY_UNAVAILABLE`」这一行**保留但降低优先级**：实测未观察到该失败模式，
   它是防御性条款而非常见路径。不建议删除（换模型后可能出现）。

3. **`agent-engine-spec.md` §9 预算**应补充 §6.3 的结论：明确预算按**累积 prompt token**
   计量而非仅 completion，并说明步数上限同时是成本控制手段。

4. **`agent-engine-spec.md` §4.3**「工具错误是给模型看的信息」这条设计**已被实测支持**，
   建议在 spec 中标注证据来源（本 spike），避免后续有人以为它是想当然。

5. **`agent-engine-spec.md` §5「Agent 循环」**建议补一条：引擎**不得**在模型消化工具错误之前
   替它重试或修正。实测表明模型自己处理得更好；引擎抢先重试反而会掩盖问题。

6. E7 的具体数值**不要现在冻结**。§6.2 是外推值，应在首个真实候选（含渲染自验证）跑通后
   用实测替换。建议 spec 写「预算上限由部署配置给出，初始值见 spike E7，首个垂直切片后校准」。

## 8. 诚实说明

- `run_command` 全程模拟，**未真实执行任何命令**。因此本 spike **不能**证明"agent 在真实
  shell 环境下也这么可靠"——它只证明了工具调用协议层面的可靠性。真实执行的安全性由 E1 负责，
  而 E1 的结论是 Windows 原生方案不足以隔离（见 `spikes/e1-sandbox/RESULT.md`）。
  两个 spike 合起来看：**协议可靠 ≠ 可以放心让它跑命令**。
- 任务复杂度单一（同一个 prompt 跑 20 次），没有覆盖不同难度、不同媒介、不同约束强度。
- 未测试并发会话下的限流行为（本次串行执行）。
