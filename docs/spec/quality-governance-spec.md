# 编辑与交付质量规范

> TS 重构 v1，2026-09-12。本文替代旧 Phase 6 门禁式治理流程。
> 质量检查用于保证共同编辑和真实交付，不要求每个小动作产生审计包。

## 1. 判断顺序

先保证设计状态正确，再评估视觉和格式交付：

1. 操作针对正确对象，人工修改不会丢失，撤销和恢复有效。
2. 内容、数据、公式与模板约束符合用户要求。
3. 构图、字体、色彩、间距、节奏和素材质量合适。
4. 实际产物可运行、可打开，并保持声明的编辑能力。
5. 四个客户端读取同一设计，不依赖旧 Python 路径。

视觉好看不能抵消数据丢失；测试通过也不能证明作品适合用户。

## 2. 编辑正确性

Document Kernel 的确定性测试覆盖父子坐标、变换归一化、组操作、文档 schema、原子命令、同属性冲突与无关属性合并、文本映射、撤销重做和版本恢复。

选择少量能揭示错误的组合案例，如“缩放视口后旋转组内对象，再撤销并导出”。不要为每个 getter 和组件文案重复写测试。

对中文输入、拖拽命中、键盘和富文本选区做真实界面验证。属性面板、画布、图层和保存重开必须一致。

## 3. Agent 交互质量

少量真实模型集成用例验证：多轮讨论、局部修改、用户拖拽后的续改、steer、停止、待答问题、压缩后的继续任务与图片输入。

确定性模拟可以测失败和并发，但不能将模拟通过称为真实模型设计成功。模型用例记录实际配置和失败即可，不建立庞大评分平台。

禁止“每轮整份重写”的退化：用户只改标题，应能看到局部操作。不能因工具循环成功结束就称为请求完成。

## 4. 视觉检查

在方向选择、大布局变更和最终交付等有意义的节点查看真实渲染。检查溢出、裁切、间距、字体、对比、层级和跨页一致性，并根据问题做针对性修复。

一次改字不要求完整视觉回归。不同媒介使用各自需要的检查，不对每个任务套固定候选数量、固定轮数或一套通用审美分数。

视觉来源带修订号；过期截图不得用于确认当前设计。用户明确选择的风格高于模型一般偏好。

## 5. 原生交付

| 产物 | 必要验证 |
|---|---|
| Web | 实际构建、关键导航/交互、响应式布局、离开 OEY 后可运行 |
| PPTX | 文件可打开；文字/图片/形状/表格/常用图表为独立可编辑对象；实际排版 |
| DOCX | 文字/表格/样式/章节结构可编辑；模板关键项与实际分页 |
| PDF | 页尺寸、内容完整、字体与来源修订，不能用它证明原生格式可编辑 |
| 项目 | 保存重开、版本恢复、CLI/TUI/图形端结果一致 |

原生文件结构检查与目标应用打开检查各有用途。画布正确不能省去 Office 文件检查；整页截图不能通过“存在一个文本框”的弱检查冒充原生幻灯片。

格式缺失项精确到对象/特性。失败文件和未完成结果不能显示成功导出。

## 6. 运行与性能

检查取消后不再写入、命令重试不重复、重连不重放副作用、崩溃不丢已确认输入、同项目多端不双写。

基础性能样本以普通设计项目为准，例如数百个对象、多页文档和中英文混排；记录测试机器、对象数量及拖拽/输入响应。手工编辑过程中不需要模型请求。

开始阶段先测真实瓶颈，再采用索引、增量渲染或后台工作。不要先承诺无限画布规模或为了假设的多人负载建设分布式系统。

## 7. 必要测试层次

- document：少量但有覆盖力的确定性操作/文本/冲突测试。
- runtime：事务、输入、取消、重连与 SDK 行为的集成测试。
- media：代表性格式夹具、原生结构和真实渲染。
- clients：CLI 无头链路、TUI 交互、Web/Desktop 直接编辑与跨端继续。
- 完整产品：三个真实创作任务及一次旧项目迁入。

每个阶段只补当前引入风险所需的测试。通过后除非有新改动、失败或未解决问题，不重复跑无关大套件。

## 8. 完成声明

实施进度引用 [实施计划](implementation-plan.md)。R2 的 Deck 编辑成功不是全量重构完成；R3 的 Pi 成功不是 Doc/四端交付完成。

本次文档修改只检查规范一致性、链接和历史效力，不报告为已完成代码验证。将来实现必须分别报告真实做了什么、如何检查和哪些能力仍未实现。
