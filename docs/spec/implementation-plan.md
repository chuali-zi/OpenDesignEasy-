# D 路线：全 TypeScript 彻底重构实施计划

> 版本：TS 重构 v1，2026-09-12；实施状态更新：2026-09-20。
> 路线已由用户选择；R1 的 Windows 开发基线已完成。R2 Deck 编辑与导出已完成本轮验收；R3 产品集成及原生、兼容服务验收均已完成。完整重构仍未完成。
> 本计划取代旧 Phase 0–6 计划和 Python/Pi 兼容路线。R0–R7 是新的交付序列。

## 1. 决策与完成范围

采用新 TS 文档内核、Pi runtime、直接编辑器、TS 资料/产物工具和四个客户端。全部一方产品实现迁移 TS，旧 Python 不参与新请求、安装、导出或数据迁移。

完整重构包含：

- 交互式 Design Agent：讨论、方向探索、局部修改、执行中纠偏、停止、问题、恢复。
- Figma 式必做编辑：拖拽、尺寸/旋转、视口、多选、图层、分组、对齐、富文本、图片、撤销/重做。
- 人工与 agent 使用同一文档、修订、操作历史与冲突规则。
- Web、Deck、Doc 的编辑模型、资料解析、渲染和真实交付。
- Web、CLI、TUI、Desktop 共用无头核心，实际实现各自产品入口。
- 旧项目迁入、新安装包、三平台验证与 Python 运行代码退役。

每个阶段可以提供有限但真实的可用路径；未做的范围继续列为未完成，不能改成“将来有需要再做”。

## 2. 为什么这样重构

用户已经明确后续会做终端和桌面，且直接编辑不可缺少。单纯把模型循环换成 Pi 无法提供对象身份、图层、撤销与双向同步；继续在 Python 和 TS 之间维护这些规则，也会形成两份业务语义。

因此，核心改造先确立统一文档与无头命令，再把编辑器和 Pi 接到同一个状态。既有设计思想、样本、用户资料与有价值的 UI 组件可以复用，旧运行契约不继续约束新结构。

TS 解决共享代码与运行栈问题，不自动解决视觉设计质量、Office 分页和任意网页可视编辑。下面把这些作为正式工程内容，避免隐藏成本。

## 3. 新结构与技术基线

采用 [架构](../architecture.md)的四 apps / 四 packages：

- apps/web、apps/desktop、apps/cli、apps/tui。
- packages/document、packages/runtime、packages/editor、packages/media。

基线：Node 24 LTS、TS ESM/npm workspaces、Pi 公共 SDK、React/Vite、Konva、ProseMirror、Electron、pi-tui、SQLite、PptxGenJS/docx/Playwright/PDF.js/TS OOXML 与 WASM OCR。

R1 已建立共享无头核心并完成 Windows 开发基线。R2 已补齐 Konva/ProseMirror 编辑器、图片/表格/图表和 PPTX/PDF/PNG。R3 将 Pi 公共 SDK 接入 runtime、Web 与 CLI，共用文档与历史，已有兼容服务路径已通过真实验证。TUI、Desktop 与其他媒介仍待对应阶段实现；跨平台干净安装留到 R7。

## 5. R1：让核心先在终端成立

建立 TS workspace、document/runtime/media 的最小可运行结构和 CLI 入口，不创建空的多层接口体系。当前这部分已形成可运行子集：

- `packages/document` 提供 Deck schema、几何与 ProseMirror 文本操作。
- `packages/runtime` 提供 SQLite 项目持久化、owner 锁、命令提交、revision、统一 undo/redo、事件和版本。
- `packages/media` 提供 R1 的基本 Deck SVG 预览。
- `apps/cli` 提供项目/文档/节点/命令/版本/事件/渲染 JSON CLI，并有真实子进程集成路径。

实现稳定 project/document/node 身份、Deck 第一批 schema、共享命令、事务提交、文档 revision、必要反向数据、SQLite 保存重开与项目 owner。CLI 能创建项目、插入/移动/改字、读状态、撤销并再次打开。

同时完成了以下兼容与核心操作检查：

- Pi 0.85.1 的隔离 faux AgentSession 注册并执行自定义工具，确认 steer 与 follow-up 到达后续模型上下文，`beforeToolCall` 确实拦截工具执行，`shouldStopAfterTurn` 在工具执行完成后停止后续模型请求，`abort` 中止真实进行中的 faux 模型请求。该验证不接触用户凭据或真实 provider，不代表产品 agent 接入；产品集成属于 R3。
- Konva 变换与文档几何的转换通过；ProseMirror 模型/文本操作可从无 UI 核心使用。
- Node 24.21.0 官方 Windows x64 binary 的 `node:sqlite` 内存读写通过；Electron 44.3.0 的真实 `utilityProcess` 在内嵌 Node 24.20.0 下也通过 SQLite 探测。
- 跨进程项目占用与重启检查通过。曾出现的 owner 测试偶发失败由 fixture 中未保留 runtime 引用、导致空闲 SQLite 连接可被 GC 回收引起；强制 GC 可复现，修正 fixture 持有 runtime 后通过，owner 实现无需变更。
- 文档命令检查覆盖图层重排最终索引、reparent 默认追加、祖先锁约束，以及无关位置修改不阻止文本步骤。

R1 的退出结果是一条真实 CLI 文档编辑路径和 Windows 开发宿主基线。Node 24 版本和 Electron utility process 均有实际 binary 结果；跨平台干净安装仍留到 R7。CLI 不需要 Web 服务或模型 key。发现库缺陷时在 TS 范围内调整具体方案，不退回旧 Python。验证细节见 [R1 兼容性与状态](r1-compatibility.md)。

## 6. R2：完成第一条直接编辑路径

以 Deck 为首个媒介，建立共享 editor、Web 宿主与文档渲染：

截至 2026-09-20，已补齐富文本、中文输入、图片原件/替换/裁切/fit/透明度、对齐/分布/吸附、框选、组内编辑、主题、表格和三类图表。实际 PowerPoint 打开混排三页并导出 PDF/PNG，发现并修正了表格的无效垂直对齐值。Chrome 4/4 覆盖基础与扩展控件，文本换行的最终视觉检查已通过。

试用当前 production UI：先运行 `npm run build:web`，再运行 `npm run web -- --project .tmp/workbench`；host 默认 `localhost:4318` 并直接提供 `apps/web/dist`。`npm run dev:web` 仅用于开发代理，不需要作为试用的第二个服务。详细配置、CLI 接续与格式边界见本轮验收文档。

- 完成 [编辑规范](editor-document-spec.md)列出的选择、视口、几何、图层、分组、对齐/吸附、富文本、图片和历史操作。
- 属性、图层与画布共用稳定 ID；一个手势一个命令，本地预演与保存状态分开。
- 支持多页、主题、原生文字/图片/形状/表格/常用图表。
- 实现 TS PPTX 生产及 PDF/截图路径，不借用旧 exporter。
- CLI 与图形编辑使用同一项目和操作，保存重开不漂移。

用三页 Deck 验证：混排文字、旋转/分组、裁切图片、表格、图表；编辑、撤销、重开和原生 PPTX 打开均正确。

此阶段可以没有智能生成，但必须是真正的设计编辑器，不能只实现选中 HTML 或拖一张整页图片。

## 7. R3：让 Pi 与用户共同创作

在 runtime 直接接入 Pi SDK，建立设计提示与工具，工具调用共享文档命令。实现项目会话、可靠输入接收、steer/follow_up、取消、待答问题、当前选区与变更上下文。

当前以上产品路径已实现。真实兼容服务完成合成资料讨论、三页生成、人工调整后扩展第四页、提问重启回答；图片生成、识图、插入和截图检查也已通过。使用现有 K3 凭据的原生 provider 补测也已通过，实际响应协议确认为 anthropic-messages，包含截图识别与设计决定工具调用；R3 验收完成。

模型配置支持 Pi 已支持的 provider 与经过验证的自定义兼容 endpoint；用原生 provider 和用户实际使用的兼容服务检查文本、工具与图片能力，不以 API 名称相似推定完全兼容。

补齐本阶段实际需要的 TS 参考读取、图片生成与截图检查。落实最近人工编辑优先、冲突重读、分批修改、统一撤销、压缩后恢复设计上下文和进程重启。

必要交互例子：

1. 用户提供材料并与 agent 讨论，确认方向后生成三页可编辑作品。
2. 用户拖动图片、调整标题，agent 沿用布局扩展下一页。
3. Agent 与用户同时改同一对象，冲突可理解；无关属性可以合并。
4. 执行中纠偏、提问与回答、取消后晚到结果，都不破坏文档。
5. CLI 运行同一 agent 工具链，图形端观察并继续编辑。

R3 完成说明交互式 Deck 路径成立，仍不代表 Web/Doc/TUI/Desktop 或整个 D 路线完成。

## 8. R4：Web 的直接编辑与源码生产

实现 WebDocument 的页面/路由、组件/DOM 语义、flow/flex/grid/定位、断点及受管 TS/TSX/CSS 模块。实际 DOM 与稳定节点映射支撑 overlay 编辑。

完成原生节点选择、重排、调整尺寸、样式和内容修改；自定义组件通过明确 props/布局边界编辑，源码修改进入同一版本。不能把任意源码编辑当成可视模型之外的旁路。

实现既有仓库的 TS 读取和受支持结构导入，能继续制作多页 React/Vite 应用。构建、导航、真实交互、响应式、ZIP/源码/HTML/PDF 均有实际产出。

用一个包含导航、表单演示和响应式布局的项目验证。任意第三方 JSX/CSS 内部无损拖拽不属于承诺，但 OEY 原生生成的对象必须可编辑，不能全部包成黑盒。

## 9. R5：Doc、模板与完整资料接入

实现 ProseMirror 正文、样式、段落/列表/表格、章节、页参数、行内与浮动对象、图形/文字混合编辑和对应历史。

完成 TS DOCX 生成、模板结构导入和必要 OOXML 保留/修改；PDF 输出与实际 Word 打开检查。模板样式、跨页表格、页眉页脚、图片锚点和中文字体是明确工作。

补齐 PDF/扫描 OCR、PPTX/DOCX、XLSX/CSV、图片和源码的实际资料解析与支持范围内的编辑导入。旧的“仅记录文件说明”不满足数据读取。

用正式报告模板和教学资料任务验证，包含杂乱截图、原文数据、表格/图片与用户手工改段落。质量结果与编辑、导出语义共同检查。

## 10. R6：完成 TUI 与 Desktop 产品

CLI 在 R1–R5 已持续承接核心能力；本阶段整理帮助、机器输出、问题/错误状态和配置体验。

实现 TUI 的持续对话、工具活动、文档树、属性修改、纠偏/停止、问题、版本和导出。实现 Electron 的完整图形编辑、本地文件、窗口/菜单、设置、核心进程与安装包。

完成四端相同配置、会话关联、项目 owner 连接与事件恢复。验证 CLI 建项目 → Web 拖拽 → TUI 续改 → Desktop 编辑导出；全程同一项目和修订历史。

Windows 先完成实际发行；macOS/Linux 的构建与运行验证进入本阶段并在 R7 结束前完成。Desktop 不能靠要求用户先启动开发服务器满足交付。

## 11. R7：完整替换与退役

用 TS 导入器迁入实际旧项目；读取前保存旧数据副本，原件保留。按可识别结构迁入设计、资料、版本与历史聊天，列出无法还原项，不重放旧工具。

在没有 Python 和旧 OEY 服务的新环境验证安装、编辑、agent、三个媒介原生导出、恢复和四端接续；实际平台测试记录与发行说明一致。

完成新产品主入口切换，删除或归档已无运行用途的旧 Python 源码、依赖声明、旧测试和启动脚本，更新 CI、打包与使用说明。旧格式导入器保留为 TS 工具，不能变成长期双栈维护。

退役时保留历史研究和用户数据；不把整个工作目录当成可删除对象。可回到已发布版本或恢复项目备份，但新版本不能通过隐藏 Python 路径完成工作。

D 路线结束需全部范围满足，不能以“核心已换 Pi”提前宣布完成。

## 13. 依赖与交付节奏

主线为 R1 → R2 → R3。R4/R5 依赖稳定的内核与共同编辑；两种媒介模型在 R1 就定义基本边界，具体行为在对应阶段补齐。

CLI 从 R1 开始伴随每个媒介和工具开发；Desktop 的 Node/SQLite 分发验证也在 R1，不能拖到 R6 才发现核心只能运行在 Web 后端。

每个阶段交付可演示用户路径及对应必要测试。中间版本可用于开发或体验，但必须显示范围；不为阶段性发布建立 Python 兼容链。

## 15. 工作量与投入判断

这已经是编辑产品与多端平台重建，不能沿用“换 agent core 数周”的估计。

以一位熟悉项目的主开发者、AI 辅助实现、采用现成基础库、按本文有限格式支持为假设，可先预留约 **16–28 个有效研发周**作为排期占位。它是高不确定性估算，不是交付承诺；R1/R2 后按真实编辑器和导出难度重估。

前几个阶段可较早得到可用的交互式 Deck，但完整 Web/Doc、四端、模板与无 Python 分发会占显著工作量。更强的任意格式导入、复杂 Word 排版或多人协作需要另外计算，不能暗含在此估算里。

选择 D 的收益是从现在起统一核心与产品行为；代价是短期无法靠保留旧后端快速交差。该取舍已随本次路线选择接受，实施阶段应围绕具体能力推进。
