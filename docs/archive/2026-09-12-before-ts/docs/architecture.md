# OEYdesign 总体架构

> 状态：已于 2026-07-24 审核通过，正式采用。
> 本文定义产品边界、系统分层、设计流程和关键职责，不绑定技术栈、字段结构、数据库、框架或 Agent 数量。
> 具体系统契约由 `docs/spec/` 承接；历史专题调研已移入 `docs/archive/`，作为决策依据保留。

## 1. 产品定义

OEYdesign 是一个面向 Web、PPT 和 DOCX 的多模态设计工作台。它接收自然语言、图片、文档、代码仓库、既有模板和品牌资产，理解用户真实意图，形成可持续修改的设计项目，并交付可运行、可编辑或高保真的真实文件。

产品不是单纯的聊天应用，也不是模板填充器。它需要同时具备四种能力：

1. 理解模糊需求、杂乱资料和参考物；
2. 形成有整体观点的内容与视觉设计；
3. 在不同输出媒介中可靠生产和导出；
4. 让用户通过预览、选择、批注和版本持续参与设计。

系统最终以易部署、可视化配置的完整应用形态交付。模型、工具、字体、品牌、模板、权限和导出设置应由产品界面管理；内部任务再复杂，也不应要求普通用户手工编排 Agent 或维护隐藏配置。

产品目标不是追求“完全无约束”，也不是追求“所有输出都标准化”，而是在设计质量、可控性、效率和交付可靠性之间按任务取得合适平衡。

## 2. 已确认的架构决策

以下方向已经确认，作为后续架构基础：

1. 当用户没有给出明确模板或强约束时，默认给予模型较大的设计空间；模板锁定是正式能力，但不是所有任务的隐含默认值。
2. 每个设计候选在一次迭代中有一个统一的创作负责人，保证内容、叙事、风格和布局的整体一致性。
3. 强结构化的交付表示主要在设计方向选定后介入；前期仍保留必要的语义结构，也允许任务主动选择模板或结构化工作方式。
4. 创作约束、运行安全和交付验证是不同的边界，分别治理。
5. 审美与目标适配、事实与交付正确性分别评价，最终共同决定是否可交付。

这些决策表达的是默认倾向，不是否定模板、设计系统、布局原语、IR 或确定性流程的价值。

## 3. 架构原则

### 3.1 设计由意图驱动

系统首先理解受众、目标、内容、使用场景和交付要求，再选择创作方式。技术表示和现有模板服务于设计意图，不能反过来成为唯一的产品定义。

### 3.2 自由度与约束分层

事实、品牌、版式、交付和运行安全可以拥有不同强度的约束。同一任务不必整体处于“开放”或“锁定”状态。

### 3.3 共享语义，媒介专用生产

Web、PPT 和 DOCX 共享需求、事实、证据、资产、风格知识和反馈历史，但各自使用适合自身媒介的设计与交付表示。系统不追求一个通用视觉树覆盖全部输出。

### 3.4 项目是系统真相

对话是操作项目的入口，不是项目本身。需求、资料、设计方向、版本、反馈、审批和导出结果都属于持久项目状态。

### 3.5 原生结构与来源优先

系统优先理解原始文件、主题、样式、对象关系和代码结构，再使用 OCR 或视觉模型补充解释。事实、模型推断和用户确认保持可区分。

### 3.6 以真实产物闭环

设计评价基于浏览器、幻灯片、分页文档和最终导出物的真实渲染结果，而不是只检查模型文本、代码或中间数据。

### 3.7 模型能力可替换

系统依赖任务能力而非某个供应商的会话格式。不同模型可以使用不同程度的脚手架、工具和工作方式，但项目状态和交付标准保持稳定。

### 3.8 创作开放不扩大安全权限

模型可以获得宽广的视觉表达空间，但文件、网络、凭据、外部发布和高成本行为始终受独立的安全与审批边界控制。

## 5. 各层职责

### 5.1 产品体验层

工作台以左侧对话、右侧真实预览为核心，并根据产物提供页面、幻灯片、章节或文件树。用户可以查看资料来源、切换候选、点选对象修改、提交批注、比较版本、恢复历史并选择导出方式。

所有模型、权限、模板、品牌、字体和导出选项最终应以可理解的产品设置呈现，而不是要求用户编辑隐藏配置。

### 5.2 项目与工作流控制层

这一层维护项目生命周期，负责任务阶段、长任务恢复、重试、用户中断、审批、版本和外部副作用。聊天刷新、模型切换或执行进程重启不应导致项目状态丢失，也不应重复执行发布、付费生成等操作。

### 5.3 上下文与证据层

这一层把上传文件、仓库、图片、模板和品牌资产转成可使用的项目知识，同时保留原件和来源关系。它区分：

- 原生解析或测量得到的观察；
- OCR、视觉模型或语言模型做出的解释；
- 用户已经确认的事实与设计要求；
- 可用于分析、可用于交付和禁止使用的不同资产权利。

它为创作提供可靠材料，但不替创作负责人决定最终构图。

### 5.4 设计智能层

这一层形成设计 brief、选择设计策略、组织候选方向、调用素材能力、进行视觉推演和吸收用户反馈。一个候选由一个创作负责人统筹；支持角色可以提供研究、文案、风格分析、模板建议、素材和批评。

设计智能层既能从空白开始，也能主动选择模板、设计系统或已有产物作为更优起点。

### 5.5 Artifact 生产层

这一层将已形成的设计意图落实为 Web、PPT 或 DOCX 的真实产物。它负责媒介适配、对象稳定性、可编辑性、分页或响应式行为、构建、导出和必要的格式转换。

生产化不是机械转码。若目标格式无法完整承载设计，它需要在保真度、可编辑性和实现成本之间做显式选择。

### 5.6 质量与治理层

这一层贯穿输入、设计、运行和交付，处理事实来源、资产权利、结构错误、视觉质量、无障碍、安全、成本和最终审批。它向设计流程提供反馈，但不会用单一规则取代所有审美判断。

## 6. 端到端设计生命周期

### 6.1 接入与理解

接收用户描述、参考图、文档、仓库、模板和品牌资产，保留原件并理解其内容、结构、用途、来源和权利。

### 6.2 意图与 Brief

形成受众、目标、输出媒介、核心内容、事实要求、风格倾向、必须使用或禁止使用的资产，以及交付标准。只有会实质改变事实、权利、品牌或结构的问题才必须追问；一般视觉歧义可通过默认方案或候选方向解决。

### 6.3 设计策略

系统根据任务决定：

- 使用多大创作自由度；
- 是否采用现有模板或设计系统；
- 哪些约束是建议，哪些是硬要求；
- 是否需要多个候选方向；
- 使用何种工作媒介表达和验证想法；
- 最终更重视可编辑、保真还是两者平衡。

### 6.4 概念与候选生成

创作负责人统筹内容、叙事和视觉，形成完整候选。候选可以从空白生成，也可以基于模板、组件、历史设计或参考物演化。多个候选可以并行产生，但每个候选内部保持单一创作责任。

### 6.5 渲染、比较与方向确认

系统真实渲染候选，结合结构检查、视觉批评和用户偏好进行比较。方向尚未稳定时，允许大幅调整、替换模板或重新设计，而不局限于局部 patch。

### 6.6 细化与生产化

方向确认后，继续完善文案、层级、素材、交互和细节，并逐步引入目标媒介需要的稳定结构。此时优先保护已确认的设计意图，修改从局部和可逆操作开始。

### 6.7 导出与验证

对实际源码、PPTX、DOCX、PDF 或部署结果重新渲染和验证。交付结果同时包含必要的质量、来源、权利和转换说明。

### 6.8 反馈与演进

用户修改、采用或拒绝的结果进入项目版本与评测记录。被证明有效的设计、模板和组件可以在审核后沉淀为组织或个人设计资产。

## 7. 自由度与约束模型

自由度不是一个全局开关，而是多个维度的组合：

| 约束维度 | 典型内容 | 可选强度 |
|---|---|---|
| 事实与证据 | 数据、结论、引用、截图证据 | 通常严格 |
| 内容与叙事 | 必须内容、篇幅、章节、顺序 | 开放到严格 |
| 品牌与风格 | 色彩、字体、语气、视觉语言 | 建议、引导或严格 |
| 构图与模板 | 网格、页面骨架、母版、组件 | 自由、可变模板或锁定模板 |
| 交付属性 | 可编辑性、保真度、响应式、分页 | 按目标格式严格 |
| 运行与权限 | 文件、网络、发布、成本 | 始终严格治理 |

系统可以提供三个易理解的预设：

- **开放探索**：事实和安全严格，视觉表达默认开放；适合原创方向和能力较强的模型。
- **设计引导**：使用品牌、参考、设计系统、模板或组件提供边界，但允许创作负责人重组和扩展。
- **规范生产**：模板、母版、合规结构和交付规则作为硬合同；适合批量、正式报告和高度一致的输出。

预设只是起点。一个渗透测试报告可以“事实与章节严格、模板严格、局部视觉引导”；一个产品官网可以“事实严格、品牌引导、构图开放、发布权限严格”。

## 8. 模板、设计系统与布局原语

模板是高价值的一等设计资产。成熟模板可以承载行业经验、品牌一致性、交付可靠性和已验证的版式，不应被视为低质量设计的同义词。

系统支持模板的四种角色：

| 角色 | 作用 | 模型可调整范围 |
|---|---|---|
| 参考样例 | 提供风格、密度、节奏和构图证据 | 完全可以重新设计 |
| 起始脚手架 | 提供可快速演化的页面或文件基础 | 可重组、替换和扩展 |
| 设计系统 | 提供 token、组件、母版和组合规则 | 在系统允许范围内创造 |
| 交付合同 | 保证品牌、合规、批量或格式一致性 | 仅修改明确开放的区域 |

模板的角色和约束强度应当显式可见。问题不在于使用模板，而在于系统把模板的限制隐藏成模型能力上限，或在用户期待严格复刻时擅自偏离。

布局原语和组件库同样如此：它们可以显著提高稳定性、速度和质量，也可以作为创作负责人的工具；只有在所有任务都被强制限制为同一小组原语时，才会损害设计空间。

## 9. 设计知识与表示层次

系统需要三种不同层次的表示，避免把“结构化”简单等同于“限制创造”：

### 9.1 共享语义核心

从任务开始就存在，承载需求、事实、证据、内容关系、资产、权利、风格知识和交付要求。它不规定具体画面。

### 9.2 创作工作表示

由创作负责人根据任务选择，可以是代码、画布、结构化页面、模板实例或混合形式。其目标是高效表达和验证设计，并不要求三种媒介共享同一种表示。

### 9.3 生产与交付表示

用于稳定编辑、对象映射、协作、导出和回归验证。它通常在方向稳定后变得更严格，但在规范生产、模板复刻或可编辑性优先的任务中，也可以更早介入。

因此，IR 不是被排除在创作之外，而是按任务选择介入时间和约束强度。早期语义结构通常必要；早期强制统一视觉结构则不是默认要求。

## 10. Design Agent 与 HTML 的关系

Design Agent 是设计意图和整体结果的负责人；HTML/CSS/JS 是它可以使用的一组表达与实现工具。

- 对 Web，经过验证的项目源码和浏览器结果可以直接成为最终产物。
- 对 PPT，HTML 或浏览器画布可以用于快速探索复杂视觉，也可以直接使用幻灯片工作表示；最终仍需根据可编辑性与保真要求进入 PPT 生产路径。
- 对 DOCX，HTML 可以辅助预览或编辑，但不能替代原生文档结构、模板、分页和引用关系。

创作与代码实现可以由同一模型连续完成，也可以分工。架构固定的是设计责任、项目状态和质量标准，而不是固定一个“HTML Agent”或把 HTML 设为跨媒介唯一真源。

## 11. Agent 职责模型

系统在逻辑上需要以下职责：

- **项目编排**：管理阶段、上下文、预算、中断和审批；
- **资料与证据理解**：解析参考物、仓库、事实、来源与权利；
- **创作负责人**：统筹候选的内容、叙事和视觉决策；
- **内容、风格与素材支持**：提供文案、研究、设计系统、模板和素材候选；
- **生产化**：把选定设计落实为目标媒介的稳定产物；
- **批评与验证**：观察真实渲染，指出审美或正确性问题；
- **导出与交付**：完成格式转换、重新渲染和交付报告。

这些是职责，不是必须独立部署的 Agent。一个强模型可以连续承担多种职责；专门模型、确定性工具和并行 Agent 只在能提高质量、速度或可靠性时引入。

单一创作责任也不排斥多候选探索：不同候选可以由不同创作负责人并行产生，但同一候选不应由多个互不统筹的角色拼接成最终设计。

## 12. 模型兼容与适配

系统以能力角色选择模型，例如深度推理、快速编辑、视觉理解、结构提取、图片生成和图片编辑，而不是让领域架构依赖某个模型名称。

不同模型可以获得不同的工作环境：

- 能力强、视觉推理稳定的模型可以获得更开放的创作空间和更直接的工作区工具；
- 较小、较快或结构化输出更稳定的模型可以使用模板、组件、明确步骤和更窄的工具；
- 图片模型负责装饰性或愿景性素材，但事实性图表、公式、知识结构和证据优先由可靠数据和确定性方法生成；
- 模型降级必须保留任务需要的视觉、文件、工具或结构化能力。

这意味着“模型无关”不是让所有模型使用同一个提示和同一套限制，而是让系统可以为模型选择合适的 harness，同时保持项目语义和交付标准不变。

## 13. 多模态参考资料与风格学习

参考资料处理遵循以下顺序：

1. 保存原件并识别安全、格式和权利；
2. 优先提取原生主题、样式、对象、关系、代码和几何结构；
3. 对缺失区域使用版面分析、OCR 和视觉理解；
4. 分离可观察事实、模型解释和用户确认；
5. 识别参考物分别承担证据、内容、素材、风格、模板或品牌约束中的哪种角色；
6. 将适合当前任务的内容交给创作和生产流程。

风格知识不仅包含颜色和字体，也包括密度、层级、节奏、图文关系、构图母题、代表性样例、组件和模板。每项知识都可作为建议或硬约束使用，并保留来源与可信程度。

参考物默认用于理解和迁移高层视觉语言；当用户明确要求复刻、模板填充或品牌一致时，系统提高对应约束强度。权利不明的素材可以用于分析，但不默认进入公开交付物。

## 14. 输出媒介架构

### 14.1 Web

Web 路径支持从开放源码创作、既有仓库修改、模板脚手架或设计系统组件开始。项目源码是主要生产载体，并维护预览对象到源码的稳定关系，使用户可以点选修改、回退和导出。

质量关注真实构建、不同视口、交互、可访问性、性能、隔离预览和部署结果。模板可以提升起步速度与一致性，但不限制系统生成新的页面结构和视觉表达。

### 14.2 PPT

PPT 路径先确定受众、叙事、大纲和视觉方向，再形成幻灯片级设计。创作可以使用自由构图、既有主题、母版、模板或可组合布局原语。

方向稳定后，系统按交付目标选择：

- 可编辑优先：更多对象保持为原生文本、图形、表格和图表；
- 保真优先：允许复杂视觉局部或整页扁平化；
- 混合方式：常规对象可编辑，复杂背景和装饰保持高保真。

最终 PPTX 必须重新渲染检查字体、换行、裁切、对象位置和 Office 兼容性。

### 14.3 DOCX

DOCX 路径更早强调事实、证据、章节、引用和模板结构，因为这些约束构成文档本身的价值。对于正式报告，用户提供的模板、段落样式、编号、表格、页眉页脚和分页规则可以直接成为交付合同。

设计仍可改善层级、可读性、图表、证据组织和版面节奏，但不能为了视觉自由破坏文档语义、模板映射或分页可靠性。最终 DOCX 和 PDF 分页结果都需要验证。

## 15. 质量与修复闭环

质量分为两个相互协作的轨道：

### 15.1 审美与目标适配

关注设计观点、信息层级、构图、节奏、连贯性、受众适配、风格一致性、素材适配和原创性。主要通过创作模型、视觉批评、候选比较、用户偏好和设计评测判断。

### 15.2 正确性与交付可靠性

关注事实来源、资产权利、格式合法、构建成功、溢出、遮挡、字体、对比度、响应式、分页、交互、可编辑性和最终导出。尽量使用确定性检查和真实渲染验证。

修复策略随阶段变化：

- 在方向探索期，可以重构、换模板或重新生成整个候选；
- 在方向确认后，优先对象级、局部、可逆的修改；
- 硬错误必须修复，审美建议则结合设计意图判断；
- 自动修复有次数和回归边界，修复后重新渲染比较；
- 高风险报告、公开发布和重大方向变化保留人工审批。

自动评分是观察信号，不是唯一裁判。最终质量由硬门槛、审美判断、用户采用和真实交付共同定义。

## 16. 项目状态、版本与人机协作

项目持续保存：

- 原始输入和解析结果；
- 已确认的需求、事实与约束；
- 候选方向、模板和设计系统选择；
- 设计产物及其可回退版本；
- 对象级反馈、修改记录和审批；
- 渲染、质量和导出结果；
- 模型、工具和转换产生的可追踪衍生关系。

系统只在重要不确定性上打断用户，例如事实缺失、权利不明、品牌冲突、方向选择或公开交付。普通布局和装饰决策由创作负责人先做出合理选择，再通过预览让用户修改。

## 17. 运行、安全与治理

长任务以可恢复工作流管理，明确阶段、重试、中断和副作用。产品状态、工作流执行状态、聊天界面状态和大型文件分别管理，避免任何单一模型会话成为系统真相。

所有上传内容和生成代码均按不可信输入处理。解析、构建、渲染和格式转换在受控环境运行；文件根、网络、进程、时间、资源和输出大小受到限制。凭据不进入生成产物的工作区。

删除、公开分享、部署、外部发送、高成本生成和权限提升需要相应审批。所有关键工具行为保留项目、用户、任务和结果关系，并能够避免重试造成重复副作用。

## 18. 评测与系统演进

架构需要支持稳定的真实案例集和回归流程，覆盖不同语言、资料质量、参考方式、模板类型和输出媒介。评测同时观察：

- 事实与来源正确性；
- 视觉偏好和任务适配；
- 用户采用率与人工修改时间；
- 构建、导出和重新渲染成功率；
- 模型切换后的行为稳定性；
- 成本、时延、恢复和审批体验。

模型版本、渲染器、模板和评价标准变化都可能改变结果，需要可比较的版本记录。高质量模板、组件、修复策略和用户偏好可以逐步沉淀为设计知识，但进入共享设计系统前应经过审核，避免把偶然结果固化为规则。

## 19. 当前不决定的事项

本文暂不决定：

- 前后端和运行时技术栈；
- Agent 框架、数据库和存储实现；
- 具体 Agent、worker 或服务数量；
- 字段、消息、事件和 IR schema；
- 模型供应商、具体模型和路由数值；
- 解析器、渲染器和导出器的最终选择；
- MVP 的具体媒介优先级和阶段排期。

专题调研中的技术建议仍然有效，但必须在具体模块设计和技术选型阶段重新按本架构排序，而不是直接成为规范性结论。
