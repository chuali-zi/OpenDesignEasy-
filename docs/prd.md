# OEYdesign 产品需求

> 版本：TS 重构 v1，2026-09-12。产品方向已由用户采用；功能实现状态见 [实施计划](spec/implementation-plan.md)。
> 本版替代旧 PRD；原始愿景保存在 [重构前快照](archive/2026-09-12-before-ts/docs/prd.md)。

## 1. 产品定义

OEYdesign 是一个跨客户端的交互式 Design Agent。用户可以通过对话、参考资料、候选比较和直接编辑，与 agent 持续共同创作 Web、Deck/PPT 和 Doc/DOCX。

设计必须有内容与视觉观点，能理解自然、模糊的需求，支持风格模仿、模板和品牌使用，并产生可运行、可编辑或高保真的真实交付。好看、好用、配置清晰和安装方便都是产品要求。

图形界面以左侧对话、右侧实时作品为基础，结合图层和属性面板；主要设置均可视化操作。保留多模态输入、模型切换和自定义兼容 API endpoint 的要求，通过 Pi 的模型接入能力实现，按实际验证展示各模型支持的功能。

## 2. 已采用范围

1. 全部一方应用代码、领域逻辑、agent 工具、解析、渲染、导出、迁移和交付脚本迁到 TypeScript。
2. Pi SDK 负责通用 agent 会话与执行，新应用不依赖旧 Python 后端或其兼容服务。
3. 图形客户端必须支持自由拖拽、对象缩放/旋转、画布缩放和平移、多选、图层、分组、对齐、富文本、样式、撤销重做与版本恢复。
4. 人工编辑与 agent 编辑双向同步，共享同一设计文档和操作历史。
5. Web、CLI、TUI、Desktop 是正式交付范围，共用核心；不能只做 Web 后把其他客户端留成设想。
6. Web、Deck、Doc 都是正式媒介；阶段选择首个媒介不改变最终范围。

“全部 TS”指我们维护的产品实现；CSS、HTML、JSON 等样式、模板和配置资源照常使用。第三方 Chromium、SQLite、图像/OCR 的原生或 WASM 引擎可以使用，前提是安装和运行不要求 Python 服务或 Python 工具链。

## 3. 用户场景

### 3.1 模糊意图与视觉探索

用户提供项目仓库和演示照片，希望制作介绍。Agent 理解受众、用途、事实和素材，必要时提问，或展示有差异的视觉方向；选定后持续制作。用户明确要求直接完成时，agent 可以直接推进。

### 3.2 人工与 agent 共同编辑

用户拖动封面图片、缩放文本框、在图层面板重排对象，随后说“沿用我刚才的布局，扩展下一页”。Agent 读取更新后的文档，保留手工修改。Agent 修改颜色与文案后，画布、属性面板和图层立即反映结果。

### 3.3 教学演示

根据离散数学资料制作演示，叙事、公式、图表、知识结构与说明连贯。配图按实际用途生成；准确公式与数据图使用可验证的文字、矢量或图表对象，不把事实正确性交给装饰性生图。

### 3.4 正式报告与模板

输入杂乱截图、文字和现有 DOCX 模板，整理出有条理且符合模板要求的报告。保留证据来源、用户确认事实和必要的模板样式；用户能编辑文本、表格、章节与插图，随后导出 DOCX/PDF。

### 3.5 跨端继续

CLI 中导入资料并启动设计，TUI 中纠偏和查看层级，Desktop 中拖拽编辑，Web 中打开同一个项目继续。客户端切换不会复制出另一份设计状态。

## 4. 直接编辑必做能力

| 能力 | 要求 |
|---|---|
| 选择 | 单选、多选、框选、层级选择、从画布到图层定位 |
| 视口 | 平移、缩放、适应画布；视口变化不修改对象尺寸 |
| 几何 | 拖拽、缩放、旋转、比例保持、坐标与尺寸属性输入 |
| 层级 | 新建、复制、删除、排序、分组/解组、隐藏/锁定 |
| 排列 | 对齐、分布、吸附、参考线、父容器坐标转换 |
| 内容 | 富文本、字体/字号/行距、图片替换/裁切、颜色/描边等 |
| 媒介 | Deck 自由画布；Web 流式/响应式与定位布局；Doc 正文流与浮动对象 |
| 历史 | 一次手势一次撤销；人机统一的操作历史与设计版本 |
| 协作 | 冲突可理解，不静默覆盖用户新修改；执行中可补充和停止 |
| 输入可达性 | 常用操作支持键盘与属性面板，不仅支持拖拽 |

自由编辑按媒介的真实语义实现：Web 流式元素拖动改变顺序/容器或明确的定位属性；Doc 正文重排与浮动图片移动不能一律变成绝对坐标。详情见 [编辑规范](spec/editor-document-spec.md)。

## 5. 客户端范围

| 客户端 | 核心能力 |
|---|---|
| Web | 对话、完整可视编辑、参考资料、版本、设置与导出 |
| Desktop | 共享图形编辑器，加本地文件、窗口、打包与系统集成 |
| CLI | 非交互命令、JSON 输出、项目/节点操作、agent、渲染、导出 |
| TUI | 终端持续对话、计划/工具活动、文档树、选择、纠偏、问题与版本 |

CLI/TUI 不模拟终端中的鼠标画布，但可使用相同语义修改文档并生成预览。图形渲染/导出可以启动无头引擎，不能要求用户启动 Web UI。

## 6. 产物与可编辑性

- Web：可运行源码与构建产物，支持多页、响应式和实际交互；静态页面与 React/Vite 项目均有生产路径。
- Deck：原生对象编辑模型；导出 PPTX 中的文字、图片、基础形状、表格与图表保持相应可编辑能力。
- Doc：结构化正文、样式、表格、列表、图片、页眉页脚与分页；导出 DOCX/PDF。
- 三者支持项目保存、版本和适用的 ZIP/源码/Markdown 导出。

复杂外部格式无法完整识别时，保留原件及具体不支持项；这不能成为把全部产物降级成截图或把直接编辑移出范围的理由。导入支持范围与退出条件见 [生产规范](spec/artifact-production-spec.md)。

## 7. 设计与交互原则

讨论可以只讨论；探索可以展示候选；明确任务直接执行；局部编辑保护已确认内容。用户选择和手工编辑优先于模型默认风格。视觉质量基于真实结果，事实、解释、推断与确认应可区分。

系统保留结构化文档以支持编辑，但不固定套用模板、卡片数量或两个视觉主题。前期也可有素材与概念草图；被采用并声称可编辑的设计必须进入文档模型。

## 8. 完成标准与范围边界

D 路线完成需要四种客户端、三种媒介、直接编辑、人机同步、TS 导入/导出、恢复与无 Python 分发全部落地。一次自然语言生成、一张可拖动图片、只读 DOM 点选、仅预留 CLI 接口均不足以满足要求。

多人互联网实时协作、任意第三方组件内部的无损可视化编辑、完整复刻 Figma 全部功能、完整覆盖 Office 所有历史特性，不是当前完成定义。已规定的自由拖拽、图层、双向同步与主格式能力不可因此延后为可选项。

对尚未实现的功能如实标记；试验用于选择具体实现，不重新讨论是否退回 Python。
