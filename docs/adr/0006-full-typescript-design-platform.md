# ADR-0006：全 TypeScript 的交互设计平台

> 状态：**已采用**。
> 日期：2026-09-12。
> 决策来源：用户明确选择 D 路线，要求完整直接编辑与人机双向同步，并计划 CLI、TUI、Desktop。
> 实现状态：仅规范已更新，代码尚未重构。

## 背景

现有主产品是 Python Studio 与 TS Web UI，保留聊天、预览、资料、图片和导出能力。旧 Phase 6 另有冻结运行与治理契约。

产品目标已经明确为持续共同创作的 Design Agent。用户要求自由拖拽、尺寸/旋转、图层及与 agent 双向同步。单换模型工具循环不能补齐设计文档、编辑器、历史和多客户端核心。

既然用户决定最终迁移 TS，继续建设 Python/Pi sidecar、旧 API 兼容层或暂留 Python 导出，会在新交互上增加长期双栈成本。

## 决策

1. 全部一方产品实现迁为 TypeScript，包含核心、工具、解析、生产、数据迁移和交付逻辑。
2. 新 runtime 直接组合 Pi 公共 SDK，不自建第二个工具循环，不建设通用旧引擎适配平台。
3. 设计文档从创建起结构化，采用共享身份/操作加三媒介特定 schema。
4. 人工和 agent 经同一提交入口修改文档，共用修订、冲突和线性撤销历史。
5. Web/Desktop 提供完整直接编辑器；CLI/TUI 通过同一无头核心持续工作。
6. Web、Deck、Doc 与四个客户端都属于本次完整路线，不是可选远景。
7. 旧实现保留作比较与一次性导入来源，最终从产品运行路径退役。

第三方原生/WASM 引擎允许使用；安装与运行不依赖 Python。CSS、HTML、JSON 等样式、模板和配置格式照常使用，全 TS 不要求把这些声明性资源改写成程序。

## 具体技术方案

采用四 apps / 四 packages；Node LTS、Pi SDK、React/Vite、Konva、ProseMirror、Electron、pi-tui、SQLite 及 TS 媒介生产工具作为基线。细节见 [架构](../architecture.md)。

用户采用的是战略路线和范围。具体库组合是本方案的工程选择，尚需实现验证；可以在 TS 内替换不满足需求的库，不可借机缩减直接编辑或恢复 Python 依赖。

选择 Konva 的图形基础与自有文档模型，是为了控制三媒介语义与历史；它不提供完整编辑产品。富文本库和 Office 生成库也只承担其明确能力，不能推定拥有任意文件无损往返。

## 被替代的决策

ADR-0001～0005 作为旧架构记录保留。其 Python runtime、provider binding、Windows AppContainer、受限 framework profile 等约束不适用于新产品。

旧“源码/HTML 为主要工作真源，后期才收敛结构”的口径被替代。新模型仍允许受管源码和开放设计探索，但被声称可编辑的对象必须有稳定结构与操作语义。

旧 Phase 6 的状态、门禁、验证记录和代码存在性，不证明新路线已经实现。

## 取舍与影响

收益：核心与四端共享业务规则，人机编辑有统一状态，解析/生产与 agent 工具处于同一语言栈，后续客户端无需重新迁移核心。

成本：需要真正建设设计编辑器、文本与坐标系统、原生格式映射、持久化和跨端分发。Pi 不会自动提供这些能力。原生导出和任意 Web 源码编辑仍有明确范围与工程难点。

不承诺未来永不重构，也不将完整复刻 Figma、所有 Office 历史特性和互联网多人协作纳入当前范围。

## 实施

按 [R0–R7 实施计划](../spec/implementation-plan.md)推进。当前只完成文档，旧代码尚未删除。最先交付无头命令和结构化编辑，再接入 Pi 共同创作；三媒介与四端最终全部落实。
